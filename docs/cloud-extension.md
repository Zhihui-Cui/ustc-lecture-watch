# 拓展思路：服务器常驻与邮件通知

这是供有兴趣的开发者继续实现的方案，不是已完成学校端验证的部署教程。仓库主程序仍是需要图形界面、手动登录的本地版本。

## 可以如何扩展

```text
本地官方页面手动登录
         ↓
保存登录状态和固定的查询范围
         ↓
服务器验证登录状态能否恢复
         ↓
每分钟查询全部分页 → 识别新增报告 → 允许选课时提交
         ↓                         ↓
发现新增提醒                  成功 / 拒绝 / 结果不明通知
```

可以复用 `lecture_watch.py` 中的 `ListRequest`、`read_all`、`observe`、`SUBMIT_JS` 和状态文件逻辑，新增无界面运行入口和通知模块，不必重复维护两套去重算法。

## 首先验证学校登录能否迁移

Playwright 可以保存、恢复 Cookie 和 localStorage 等登录状态；sessionStorage 可能需要额外保存和恢复。参考[官方认证文档](https://playwright.dev/python/docs/auth)。

但学校可能将会话绑定到 IP、设备或校园网环境。应先实现一个 **只读 check**：在目标服务器恢复登录，读取并核对完整报告列表，不报名、不改写基线。

只有实际通过只读检查后，再考虑启动自动选课。不要默认复制登录文件后就能长期免登录；验证码、二次认证、会话过期仍需本人处理。

登录状态文件包含敏感凭证，必须仅存放在本人可控设备，不提交 Git。保持相同账号和筛选范围，迁移时携带已有基线，并停止本地自动选课，防止两边重复提交。

## 邮件通知建议

可用 Python 标准库 `smtplib` 和 `email.message`，配合自己的 SMTP 服务。SMTP 用户名、收件人和授权码应由每个使用者自行配置，不硬编码维护者邮箱。

- QQ 邮箱等服务通常使用独立的 SMTP 授权码；以邮箱官方文档为准。
- 使用服务商支持的 TLS 连接，不把密码写入仓库或日志。
- 发现新报告、选课结果、持续故障、故障恢复时才通知；无变化时保持安静。
- 以事件编号去重，失败邮件保存在待发送队列，之后重试；合并同一轮通知。
- 不要让邮件发送失败导致重复选课；SMTP 接受邮件也不保证立即进入收件箱。
- 服务器完全停机或断网时，本机程序无法发送故障邮件。如需覆盖该情况，可另外设计外部存活监测。

建议事件键：`new:<BGBM>`、`result:<BGBM>:<status>`、`failure:<incident>`、`recovery:<incident>`。

## 常驻服务建议

可尝试 Linux + Playwright Chromium 无界面模式，使用 systemd 或容器管理进程。学校连通性、浏览器依赖和真实资源占用必须在目标环境测量后确认；不必为此购买 GPU。

- 使用独立的非 root 运行用户。
- 将登录凭证、状态和通知队列放在权限受限的持久目录。
- 配置开机启动、异常重启和日志轮转。
- 保留单实例锁；采用原子写入，提交前先持久化 `submitting` 状态。
- 重启遇到未完成的提交时，标记为结果不明，等待本人核实。
- 查询失败不应更新基线或提交选课；连续失败后通知用户检查登录或网络。
- 提供明确的暂停、恢复和停止方式。先测试完整流程，再长期运行。

## 可贡献方向

1. 可配置的只提醒模式，以及主题、院系、时间冲突和报名数量限制。
2. 持久化通知队列和脱敏诊断信息。
3. 登录失效检测与本人重新认证流程。
4. 已在目标云平台验证的部署文档和资源测量。
5. 更稳定的分页快照、筛选范围变更保护和恢复测试。

请使用模拟响应测试，不把学校账号、真实 Cookie、邮箱授权码或个人选课记录放进测试样例。
